## Context

See `proposal.md` for motivation and `specs/academic-deliverables/spec.md` for the collection contract. The collection already uses collection variables and stores a bearer token after login. Broker creation checks for an existing owner/CNPJ pair before calling external data providers; API request validation and broker lookup already return the specified error codes.

## Goals / Non-Goals

**Goals:** Add examples that match the current validation and broker contracts, use the existing collection authentication flow, and make response checks and ordering visible to a person running the collection.

**Non-Goals:** Change API behavior, add test-only endpoints, or introduce credentials and external dependencies.

## Decisions

- Add the invalid-input, missing-resource, and duplicate requests to the existing `Corretoras` folder. This keeps these examples beside the registration and lookup requests whose contracts they exercise.
- Use an invalid CNPJ rejected by request validation for the 400 example, a high positive `Long` ID for the 404 example, and the existing valid CNPJ variable for a second broker registration for the 409 example. The duplicate example must state that the normal broker registration request for that CNPJ has succeeded earlier for the same account.
- Add Postman response scripts that assert the expected status for each error example. Use collection variables for the base URL, token, and existing CNPJ so the requests remain consistent with the collection's configuration model.

Alternatives considered: using stock registration for the duplicate example would exercise an external market-data provider before reaching persistence; the broker service checks duplicates before its provider calls, making the broker example more direct. Using invalid JSON would only demonstrate parsing failure, while invalid CNPJ exercises the existing domain validation contract.

## Risks / Trade-offs

- [The duplicate example depends on a successful initial broker registration and available provider integrations] → State the prerequisite in the request description and place it after the normal registration request; the repeat itself is rejected before provider calls.
- [A fixed not-found identifier could exist in a manually populated database] → Use the maximum positive signed 64-bit ID, which cannot be generated by normal database identity allocation in this application.
